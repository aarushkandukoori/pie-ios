Overview

Pie (SOSP '25) is a programmable serving system: instead of a fixed generation loop, applications ship small WebAssembly programs — inferlets — that program the serving loop itself: branch and rewind the KV cache, persist it under a name, apply custom sampling. This project ports Pie to the place where programmable serving may matter most: a phone in someone's pocket, where the data is personal and the network is optional.

The result so far is Pie Voice, an iOS app you hold a spoken conversation with. Speech is transcribed by the OS recognizer (on-device on real hardware — the app's header badge reports the actual mode), answered by Qwen3-0.6B running through the Pie engine embedded inside the app, and spoken back. iOS forbids JIT compilation, so inferlets execute under wasmtime's Pulley interpreter — permissible because Pulley generates no code at runtime (no writable-executable memory). The interpretation overhead is acceptable because inferlets are control-plane code; the FLOPs live in the native driver.

What makes it a Pie app rather than a chat wrapper: the conversation's KV state lives inside the engine under a named snapshot, carried across turns by the voice-chat inferlet. A follow-up question prefills only the new utterance — not the whole transcript. The numbers are in the benchmarks; you can watch the cost not being paid in the app walkthrough below, and feel the baseline cost it removes in the browser demo.

Try It — In Your Browser

This is a browser recreation of Pie Voice: the same base model (Qwen3-0.6B, in WebLLM's q4f16 quantization rather than the app's Q4_K_M GGUF), the same conversation design, running entirely in your browser via WebLLM and WebGPU. Nothing you type leaves this page — the model runs in this tab, and the only network traffic is the one-time model download. Voice input uses the browser's Web Speech API, which some browsers (Chrome, Edge) process on the browser vendor's servers — type instead if you want strictly local input.

What this demo deliberately shows: the browser engine has no per-conversation KV snapshots, so every follow-up re-sends and re-prefills the whole history — watch the prefill number in the stats chip grow each turn. That growing number is exactly the cost the Pie engine removes in the native app, where follow-up prefill stays flat.

Benchmarks

Measured on the app itself — the numbers below are read from the app's per-turn stats chips during a five-turn spoken conversation, recorded in one take on 2026-08-23. Utterances came from the app's bundled sample recordings (synthesised speech played into the same recognition path as the microphone), so the run is repeatable. Environment: iOS Simulator (iPhone 17 Pro, iOS 26.0) on an Apple M-series Mac; CPU-only ggml driver; Qwen3-0.6B Q4_K_M; inferlets interpreted by wasmtime Pulley. These numbers come from the Mac's CPU via the Simulator and are not predictive of iPhone hardware in either direction; a Metal driver and physical-device measurements are the next milestone.

Prefill/reuse token counts are exact and deterministic — they are the engine's own accounting, and they are the point: follow-up prefill stays flat as the conversation grows.

Architecture

The app is three layers behind three protocols, and the Pie-facing layer is the only one that knows Pie exists. Everything version-specific — engine config, model path, inferlet id — lives in one file (PieRuntimeConfig.swift), so upgrading to a new Pie release is a diff to that file plus a rebuild of the C shim.

The turn loop is the Pie thesis in miniature: which tokens to prefill, where the conversation state lives, and what is allowed to reach the speaker are all decisions made by a replaceable user-level program — not by the engine.
